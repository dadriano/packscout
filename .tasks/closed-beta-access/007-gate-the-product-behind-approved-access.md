# Task: Gate the Product Behind Approved Access

**ID:** closed-beta-access/007
**Depends on:** closed-beta-access/001, closed-beta-access/006
**Blocks:** closed-beta-access/008, closed-beta-access/011
**Estimated scope:** large
**Status:** done

## Objective

Every product surface except the landing page and the operational probes requires an admitted account, decided on the server before anything renders — so unadmitted visitors never receive gated markup, gated data, or a flash of either.

## Context

PackScout's pages are server-rendered with catalog data already embedded, so a browser-side check is not a gate: by the time client code could redirect, the data has already been delivered. The decision has to happen on the server, before render.

That is the hard part, because the product's authentication is currently client-side only — the hosted provider's session lives in the browser and the backend verifies its tokens directly. The server therefore needs its own way to know who the visitor is: the provider issues a server-verifiable identity token, and establishing that server-side signal is part of this task. The builder chooses the mechanism; the requirement is that the server, not the browser, decides.

The approved reference web app's routing model is the template: a small explicit set of public paths, everything else protected, and a separate holding area for signed-in accounts that are not yet approved — with the standing rule that a cached token can be stale, so authoritative checks re-read the real decision rather than trusting what the cookie said at sign-in.

This task owns visitor gating and routing. Closing the backend's own data door is closed-beta-access/005; the awaiting-review and declined surfaces themselves are closed-beta-access/008.

## Requirements

- The visitor's identity is verified on the server and their effective access resolved from the product backend before a gated route renders. A client-only check does not satisfy this requirement.
- Routing outcomes are explicit and total: a signed-out visitor gets the landing page; a signed-in visitor who is awaiting review or declined gets the holding surface; an admitted visitor gets the product exactly as it exists today; and an undetermined result gets a fail-closed, non-blank state that explains the problem and offers a retry — never the product, and never a redirect loop.
- The public path set is explicit and minimal: the landing page at the root, the holding surface, health and status probes, static assets, and whatever callback or lifecycle paths the authentication provider itself requires. Every other path is gated, including the dashboard, the repacks surface, learn articles, and the frontend's own data-serving routes.
- The frontend's own routes that serve catalog or search data require an admitted caller and refuse others with a stable, non-leaking outcome. The health probe stays open. Telemetry intake must not become an unauthenticated channel for product data.
- Gated surfaces are excluded from search indexing while the beta is on; the landing page remains indexable, and any robots or sitemap surface reflects that split.
- No flash of gated content and no redirect loop, including for the lazily-booted authentication provider: a signed-out visitor on the landing page must still not pull the provider before intent, and a returning session must not bounce between surfaces while the provider initializes.
- Decision changes take effect promptly: a revoked or declined user loses the product on their next navigation. Any per-request reuse of a resolved decision is short-lived and documented, and never outlives a decision change in a way the user can observe.
- The gate adds at most one bounded backend resolution to a request path; it must not multiply round trips per rendered page or make an unavailable backend look like an admitted visitor.
- Signing out is reachable from every gated state, so nobody can be stuck signed in as the wrong identity.
- When the beta switch is off, the product is fully public again exactly as today: the landing page no longer intercepts the root, gated routes render for anyone, and the indexing exclusions lift.
- Behavior specifications that currently assert full public browsing — notably the authentication feature's scenario stating that an anonymous visitor keeps full public access — are updated to describe beta-gated access. No test is deleted to make the gate pass; tests are rewritten to the new truth.

## User-Facing Behavior

A stranger opening any PackScout URL during the beta gets the landing page. Signing in either drops them straight into the product (allowlisted or already approved) or onto the holding surface. An admitted user browses exactly as before. Someone whose access is revoked finds themselves on the holding surface at their next click, without having to sign out. If the backend cannot answer, the visitor sees a clear "we can't confirm your access right now" state with a retry, not the product and not a blank page.

## Interface Contract

- Server-side gating resolves the visitor's identity and consumes the effective-access resolution and gate-status read from closed-beta-access/001; it does not re-derive admission rules locally.
- It renders the landing surface from closed-beta-access/006 for unadmitted visitors at the root, and hands awaiting-review, declined, and suspended visitors to the holding surface owned by closed-beta-access/008, passing the reason so that surface can say the right thing.
- The frontend's data-serving routes gate on the same resolution and refuse with a stable, non-leaking outcome.
- The gate reads the beta switch through the backend's gate-status read rather than any client-visible configuration.
- Read-path credential handling for catalog reads belongs to closed-beta-access/005; this task does not duplicate it.

## Acceptance Criteria

- [x] A gated route requested by a signed-out visitor returns the landing experience and no gated markup or catalog data.
- [x] Awaiting-review, declined, and suspended visitors reach the holding surface with the correct reason; admitted visitors reach the product unchanged.
- [x] An undetermined access result produces a fail-closed retry state — never the product, never a blank page, never a loop.
- [x] The frontend's data-serving routes refuse unadmitted callers with a stable non-leaking outcome; the health probe stays open.
- [x] Gated surfaces are excluded from indexing and the landing page is not, while the beta is on.
- [x] A revoked user loses the product on their next navigation without signing out; signing out is reachable from every gated state.
- [x] With the switch off, every route behaves exactly as it does today, including the root rendering the dashboard for anonymous visitors.
- [x] The authentication feature's public-access behavior scenarios are updated to describe beta-gated access rather than contradicting it.

## Spec Compliance

- Related specs reviewed: `.tasks/closed-beta-access/_index.md` (dual-purpose root, three-door enforcement, reference routing model); closed-beta-access/001 (effective access, gate status, establishment — consumed, not re-derived); closed-beta-access/006 (landing surface contract, intent-based provider boot); closed-beta-access/008 (holding surface it will replace); closed-beta-access/005 boundary (read-path credential handling untouched — this task decides who gets a page, not how catalog reads authenticate).
- Mechanism — the server-side identity signal. The client mirrors the provider-issued identity token into the `packscout-identity` cookie (`SameSite=Lax; Path=/`, `Secure` on HTTPS, written by `components/auth/IdentityCookieSync.client.tsx` inside the lazily-booted provider tree, so a visitor who never asks for authentication never gets a cookie and the intent-based boot is untouched). The cookie is transport, never trust: `lib/access-gate.server.ts` reads it per request, requires a compact-JWS shape, and resolves the visitor by calling the backend self-read (`api.productUserAccess.getMyAccess` via `fetchQuery` from `convex/nextjs` with `{ url, token }`), where Convex verifies the JWT against the provider's JWKS. Anonymous requests resolve only the gate-status read (`getGateStatus`). Cookie lifetime is derived from the token's own `exp` minus a 60s margin, clamped to 1h; the client refreshes it every 10 minutes, on session changes, and when a backgrounded tab returns, and sign-out clears it in the logout path itself. Session establishment now calls `establishAccess` (same directory write path as the old `recordSignIn`, plus the awaiting-review default), keeping the record the gate routes on fresh.
- Routing is total and server-decided. One decision type (`public | admitted | signed_out | held(awaiting_review|declined|suspended) | undetermined`) drives three pure mappers: the root serves the product (public/admitted), the landing surface (signed_out), or redirects to `/access` (held/undetermined); every gated page redirects signed_out→`/` and held/undetermined→`/access` before any read; `/access` re-resolves server-side (never trusts the URL), renders the holding notice for held/undetermined, and redirects everyone else to `/` — a pair that cannot cycle on any single decision (proven in `lib/access-gate.server.test.ts`). Undetermined is a fail-closed, non-blank retry surface, never the product; an unconfigured or unreachable backend resolves undetermined, and each backend read is bounded by a 5s timeout.
- Public set (explicit, minimal): `/` (landing for unadmitted visitors), `/access` (holding surface), `/api/health` (liveness only), `/robots.txt`, static assets (`_next/*`, favicon, brand images), and the telemetry intakes (`/api/telemetry`, `/api/public-read-failure` — justified below). The authentication provider needs no dedicated callback path: its hosted flows return to the initiating page, and the landing root is public. Everything else is gated: `/packs`, `/learn`, `/learn/[slug]`, and `/api/collectibles/search`, which now requires an admitted caller (guard runs before parsing; refusals are fixed non-leaking bodies — 401 `ACCESS_REQUIRED` for signed-out/held, 503 `ACCESS_UNAVAILABLE` for undetermined; the search fetch sends same-origin credentials so the cookie reaches the guard).
- No gated data to unadmitted visitors, including the streamed payload: every gated page resolves access before its first read (`app/route-access-gate.source.test.ts`), the guard test "an unadmitted request never reaches the catalog search read" proves the data route, and the landing/holding surfaces plus the gateway shell perform no catalog read at all. Because gated segments have `loading.tsx` boundaries, an unadmitted document request streams as a 200 whose body is the empty shell plus the redirect instruction and a `<meta http-equiv="refresh">` fallback — verified over HTTP to contain no catalog markup or data (component code in static chunks is code, not data; catalog data only ever travels as render payload after an admitted decision).
- Shell: the layout seeds a server-resolved shell face from the same cached resolution the page uses; the gateway face (landing, holding, unavailable) drops primary navigation, catalog search, and the release-status widget while keeping brand, theme, and the account control — so sign-out is reachable from every gated state (the holding copy points at it). Pages re-declare their face on soft navigations through a reporter, mirroring the release-status pattern, so crossing the gate re-dresses the shell without a full load.
- Indexing: the root's metadata follows the decision (indexable `LANDING_METADATA` for unadmitted visitors; noindex product metadata for admitted ones while the beta is on; today's untouched defaults when off). Gated pages emit `robots: noindex, nofollow` whenever the switch is not known to be off. New `app/robots.ts` (served dynamically) allows `/` and disallows `/access`, `/api/`, `/learn`, `/packs` while the beta is on or unknown, and returns unrestricted `Allow: /` — the pre-beta shape, which shipped no robots file — when it is off. `/access` is noindex in both positions. No sitemap surface exists, so none had to change.
- Freshness and reuse bounds (documented here per the spec): the identity decision is never cached — each document request re-resolves it (React `cache()` dedupes layout + metadata + page within one request), so a revocation bites on the very next navigation; the only cross-request reuse is the anonymous gate-status read, cached per server process for `GATE_STATUS_TTL_MS = 30s` (successes only — failures are re-asked), so a switch flip reaches every instance within 30s; the cookie can outlive a decision by nothing (it carries identity, not admission) and outlives the token never; the client router's dynamic staleTime is 0 in this Next version, so soft navigations re-fetch — the one client-side window is the browser's in-memory back/forward restore of an already-delivered page, which cannot fetch new data because the data route refuses. Round-trip budget: at most one uncached backend resolution per request (`getMyAccess` for identified requests, nothing extra for anonymous ones), plus the amortized TTL refresh of `getGateStatus`; a cold-cache identified request is the worst case at two.
- Hand-off to closed-beta-access/008: the route is `app/access/page.tsx`; the placeholder it replaces is `components/access/AccessHoldingNotice.tsx` with prop contract `reason: "awaiting_review" | "declined" | "suspended" | "undetermined"` and all copy in `lib/access-holding-content.ts` (distinct per-state title/kicker/heading/body, account-menu note, retry action only for undetermined); the sign-out affordance is the shell account menu, present in the gateway face; the live reaction to decision changes, the verified-identity display, and the contact path are 008's, as is replacing this copy.
- Divergences: (1) `/welcome` is retired — the root is now the landing surface's address for every unadmitted visitor, so the standalone copy from 006 would only compete with it in crawlers; its coverage moved to the root wiring in `landing-surface.source.test.ts`. (2) The telemetry and public-read-failure intakes stay open rather than gated: they are same-origin-locked, parse-then-drop POST surfaces whose responses are fixed vocabulary strings (behavior-tested), so they serve no product data to anyone; gating them would break beacons from the public landing while adding no confidentiality. (3) Unadmitted redirects under `loading.tsx` stream as 200 + redirect payload rather than a status-level 307 (Next's streaming shape); the body is data-free and carries a no-JS meta fallback. (4) A backend identity refusal is recognized by the `AUTH_REQUIRED` error code and, conservatively, by the platform's unauthenticated transport error; every other failure is undetermined — refused credentials land on the landing page, outages on the retry surface, and neither is ever admitted. (5) The local mock-convex lane predates the gate functions, so against it the frontend now fails closed to the retry surface — correct behavior for a backend that cannot answer; the browser smoke below used a scriptable stub instead. (6) `establishAccess` replaced `recordSignIn` in the session recorder (001 kept both funnelling through one write path for exactly this hand-over).
